# Security hardening — closeout status

This document first recorded a plan for the six findings in `docs/QUALITY-CONFIDENCE.md` §5 and `docs/roadmap/pc-continuation.md` against the tree at HEAD `4c3f6fc`. The three security-wave days are now built ahead: 2027-01-12 carries the protocol security gates, 2027-01-13 the integration QA fixes and 2027-01-14 the documentation and release consolidation. Code for all three is written now; the commits are held to those dates and no earlier date carries them. The plan text below is kept so each gap still states its intended change and evidence. Each gap and wave now carries a landed, landed-in-part or open status, and the status paragraphs name the files and seams on disk that support the claim.

Absolute security cannot be proven. A passing test shows that a path behaved as asserted for the inputs supplied; it does not show that the path is free of other inputs that break it, that the build contains no exploitable dependency, or that an out-of-band fingerprint exchange was not subverted. None of the work described here is complete. Each gap stays open until a change lands with its tests and a recorded observation at the stated evidence level. A design review, including the parked designs in `docs/roadmap/trust-gate-cert-binding.md`, is not evidence.

The last recorded full test run passed 972 tests; that figure is a historical run, not a current green claim. The release assembly completed green after the R8 keep-rule fix in `app/proguard-rules.pro`, and its result has not been recorded. No green rig is claimed for 2027-01-14 until that rerun is known with zero failures, zero errors and zero skipped cases. The 778 floor stays historical at the projected 362 protocol + 112 core + 212 app + 92 harness split; the 972 figure does not re-baseline it.

## Evidence rules and re-baseline

The four labels are those in `docs/QUALITY-CONFIDENCE.md` §1. CODE is source reading; PURE is a JVM-only test of a wire rule, reducer or policy seam; SIM-HARN is an in-process run over production endpoints with real TLS inside a pipe; DEVICE is an observation on physical hardware with an attached log. Where several labels apply to a claim, the weakest one governs what may be asserted. No wave in this plan produces DEVICE evidence. The rig on the rig phone has one device and no second phone, so any row that would need a second phone, a radio path or a camera stays not verified.

The floor is 778 tests, projected as 362 protocol + 112 core + 212 app + 92 harness after the four-module split. That split is a projection until JUnit XML exists for the extended rig with zero failures, zero errors and zero skipped cases. A count is a result only from such XML; a moved case keeps its assertions and its evidence level when its module changes. Each wave that adds or relocates tests updates the rig inventory in the same change as the source change, not as a follow-up. The 778 figure stays the floor until a new green inventory replaces it. No claim in this document re-baselines that figure.

Every new path states what retries, what concludes, what keeps bytes and what survives process death. Refusals keep the existing shape: 403 with `X-Flit-Refusal: declined` for a marked prepare sender, a host-signed 200 for a Circle refusal, a quiet 200 for a delivered panic. Only a short fingerprint code is written to logs.

## Gap 1 — certificate binding at prepare

**Current code path.** `FlitEngine.onPrepare` at `app/src/main/kotlin/app/flit/share/FlitEngine.kt:1538-1560` applies `qrOnly` at `:1541` and `onlyTrusted` at `:1548-1549`. Both compare `request.info.fingerprint`, which is the caller-declared string in `PrepareUploadRequest.info` (`protocol/src/main/kotlin/app/flit/share/protocol/model/Model.kt:62-65`, `PeerInfo.fingerprint` at `:19`), against a known-device row or `FlitRoster.pinned`. `ServerCore.prepareRoute` at `protocol/src/main/kotlin/app/flit/share/protocol/server/ServerCore.kt:299-326` decodes the body and calls `delegate.onPrepare(req, peerIp)` at `:310`; it reads `X-Flit-Client` at `:316` but no certificate header. The client sends only that marker in `ProtocolClient.prepareHeaders` at `protocol/src/main/kotlin/app/flit/share/protocol/client/ProtocolClient.kt:686`, used by the prepare at `:243-249`. The existing primitive is the cert-header pattern in `ServerCore.panicRoute` at `:920-939` and `circleRoute` at `:979-1000`, with constants in `protocol/src/main/kotlin/app/flit/share/protocol/Protocol.kt:51` and `:58`. The pinned route gate must read persisted rows, not the in-memory cache, as `docs/roadmap/trust-gate-cert-binding.md:32-34` requires.

**Concrete change.** Take Option B from that design record. Add a prepare-only header constant beside `HEADER_PANIC_CERT` in `Protocol.kt`; have `prepareHeaders` in `ProtocolClient` attach the sender's base64 DER. In `ServerCore.prepareRoute`, before `delegate.onPrepare`, decode the header with size and parse checks modelled on `:925-931`, derive the SHA-256 DER digest through the same primitive as `TlsIdentity.certificateFingerprint` (`protocol/src/main/kotlin/app/flit/share/protocol/tls/TlsIdentity.kt:326-330`), and pass the derived fingerprint to a defaulted `onPrepare(request, peerIp, presentedFp)` overload so existing delegates keep compiling. `FlitEngine.onPrepare` compares that derived value with the declared string and declines when either gate is on and the two differ, or when a gate is on and no certificate arrived. The known row or roster pin remains the gate source; the presented certificate never rotates a pin. Refusals keep the `:316-320` shape and log only a short code. Gates stay opt-in and off by default, so an unmarked v2.2 sender is unaffected and a v2.2 receiver ignores the extra header.

**Tests to add.** Route-level protocol tests in the style of `protocol/src/test/kotlin/app/flit/share/protocol/ProtocolRefusalTest.kt` and `CircleHardeningTest.kt`: gate on with no header, claimed/presented mismatch, malformed and oversized DER, marked and unmarked senders, and refusal headers and status. Apply each over the Ktor-backed server, the in-memory `LinkServer` pipe and the Bluetooth/relay harness carriers, since the design record at `:65-66` names those cases. Add an app-side decision test for `FlitEngine.onPrepare` with the derived fingerprint, and a restart case showing the persisted row, not the cache, is the gate source. Keep `DtoParityTest` unchanged to show no v2.2 DTO drift.

**Evidence label attainable.** PURE for the parse, digest comparison and gate decision; SIM-HARN for the in-process TCP, pipe, Bluetooth-sim and relay exchanges over production `ServerCore` and `ProtocolClient`. No DEVICE row is available.

**What remains unprovable.** The header proves consistency between a self-signed certificate and the claimed fingerprint; it does not prove that certificate was provisioned out of band. With both gates off, the declared fingerprint remains unverified by design. Because Option A is not taken, this change does not bind the TLS peer certificate; a hostile access point can still terminate the TLS session (Gap 2). Header-based identity says nothing about the physical link, a second phone or a device walk.

**Landed (2027-01-12).** `Protocol.HEADER_PREPARE_CERT` and `Protocol.HEADER_PREPARE_SIG` are defined in `protocol/src/main/kotlin/app/flit/share/protocol/Protocol.kt`. `ProtocolClient.prepareHeaders` attaches the base64 DER and a signature over the exact body bytes, so the header proves key possession rather than carrying a replayable DER alone. `ServerCore.prepareRoute` bounds the DER at `MAX_PREPARE_CERT_CHARS`, verifies the signature, derives the digest and passes it as `presentedFp` to a defaulted `onPrepare` overload. The pure decision is `core/src/main/kotlin/app/flit/share/TrustGate.kt`: bounded canonical hex, four refusal reasons, fail-closed store callbacks, a 12-character log code and both gates off by default. `FlitEngine.onPrepare` reads the persisted roster pin and known-device lists, logs the reason and short code, and binds the receive path to the presented digest. `Harness` wires the same gate over the production endpoints in-process. `ProtocolRefusalTest`, `PeerIdentityPinTest`, `TrustGateTest` and `FlitEngineTest` record the no-certificate, mismatch, malformed and oversized DER, marked and unmarked sender, refusal-shape and gates-off cases.

**Still open.** Out-of-band provisioning of the certificate is not proved. With both gates off the declared fingerprint stays unverified by design. `TrustGate` reads only the stores handed to it and writes nothing, so a presented certificate never rotates a pin. The receive-side decision still reads a header digest rather than the TLS peer certificate. No DEVICE row exists.

## Gap 2 — receiver certificate pin check for senders

The out-of-band value that should govern the check is `FlitKnown.Device.fingerprint` at `app/src/main/kotlin/app/flit/share/FlitKnown.kt:34`.

**Concrete change.** Add an expected-fingerprint input to the send path, carried on `SendTarget` or as a separate argument to `ProtocolClient.info` and `sendFiles`. Before the first prepare, fetch `info` and require a certificate in hand for the answer: add a receiver-certificate header on the info and prepare responses, derive its digest with the `TlsIdentity` primitive, and require equality with the expected fingerprint from the QR-paired known row or roster pin. An app-layer header is chosen over reading `SSLSocket.session.peerCertificates` because Bluetooth and relay pipes run TLS through `StreamTls` and expose no peer certificate, as recorded in `docs/roadmap/trust-gate-cert-binding.md:30-31`. When no expected fingerprint is configured, keep the v2.2 interop path unchanged; when one is configured and the header is missing, mismatched or malformed, refuse before any file body leaves the sender and report a concluded refusal rather than a carrier death. Fail closed on the pinned path; log only a short code. The received certificate is pinned only after its digest equals the out-of-band value, never from the header alone.

**Tests to add.** A PURE client-seam test in the protocol module: matching digest accepted, mismatched digest refused, missing header refused when an expected value exists, and the unpinned v2.2 path unchanged. A SIM-HARN rogue-receiver test in `flit-harness` that stands up a second identity with a different certificate answering `info` and `prepare`, configures the sender with the victim's fingerprint and asserts that no upload body is written before refusal. Repeat over TCP, the in-memory pipe, the Bluetooth-sim carrier and a relay route, and add a restart case where the expected fingerprint is reloaded from a persisted known row. Keep `interop/README.md` checks green for the unpinned path.

**Evidence label attainable.** PURE for the comparison seam; SIM-HARN for the rogue-receiver runs over production endpoints. No DEVICE row is available.

**What remains unprovable.** A peer holding the private key for the pinned certificate is indistinguishable from the real device. A rogue access point is refused only on a send that has a configured expected fingerprint; the default unpinned path remains exposed by design. No test covers a real radio path, ARP or DNS redirection on a phone, relay operator behavior beyond the in-process harness, or timing and power.

**Landed (2027-01-12).** `SendTarget.expectServerFp` carries the expected fingerprint. `LinkProvider.connect` and `PeerHttpClient.exchange` accept it; `TcpLinkProvider` refuses a pin on a plain carrier before any socket opens; `SocketLink.peerCertificate` reads the handshake leaf; `TlsLink` checks the pin at construction so a wrong peer receives no request byte; `TlsIdentity.checkPeerPin` is the shared comparison. `FlitEngine` supplies `expectServerFp` from `persistedPinFor(...)` on direct and relay send targets. `PeerIdentityPinTest` records a matching pin accepted, a mismatch and a rogue TLS certificate refused before any request byte, a plain-HTTP pin refused before a socket opens, legacy behavior with no pin, and piped TLS runs over `TlsLink`.

**Still open.** The receiver-certificate header on info and prepare answers is not implemented. The landed code reads the TLS peer certificate from the socket session or from `StreamTls.peerCertificate()` instead, which differs from the mechanism described in `docs/roadmap/trust-gate-cert-binding.md:30-31`. The default unpinned path stays exposed. No real radio path, ARP or DNS redirection on a phone, relay operator behavior beyond the in-process harness, timing or power is covered; no DEVICE row exists.

## Gap 3 — JOIN proof replay hardening

**Current code path.** `CircleCore.joinProofFailure` at `protocol/src/main/kotlin/app/flit/share/protocol/circle/CircleCore.kt:566-595` checks structure and signature, then the bucket at `:581-585` using `joinProofBucket` at `:474` and `JOIN_PROOF_BUCKET_MS = CLOCK_SKEW_MS` at `:56`, the duplicate-in-request rule at `:589`, and the single-use reservation `fresh(proof.id, nowMs)` at `:593`. `fresh` at `:650-658` writes the process-local `seen` map declared at `:95`, bounded at `MAX_SEEN = 4096` (`:33`). `ServerCore.circleRoute` calls the gate at `ServerCore.kt:1005-1015`. `docs/completions/2026-12-22-join-proof.md:135-145` records that a captured proof is single-use only in-process and that the bucket is the stateless backstop.

**Concrete change.** Introduce a replay-store port in the protocol module with an atomic `checkAndReserve(id, nowMs)` operation and a default in-memory implementation that preserves current behavior. Wire an instance through `ServerCore` configuration into `ServerCore.circleRoute`; the app supplies an implementation backed by a persisted store keyed by proof id, pruned by timestamp and bounded in row count. The stateless rules — domain-tagged nonce, one-key body, signature and bucket grid — remain unchanged; only the reservation at `:593` moves behind the port. When the durable implementation is selected and unavailable, the route refuses rather than silently reverting to process memory, and logs that decision. No DTO field, route or status changes.

**Tests to add.** PURE tests with a fake durable store: reserve the same id across two reconstructed gate instances and assert the second is `join proof replay`; prune old rows and assert bounded size; race two concurrent reservations and assert one winner; keep the three refusal strings and their precedence exact. SIM-HARN tests run two `ServerCore` hosts sharing one store in-process, replay a captured proof to the second and assert a signed refusal, plus a harness case that recreates the host object over a persisted store between joins. App-side adapter tests use a JVM fake store before any Android-backed adapter.

**Evidence label attainable.** PURE for the port, the store reducer and the failure gate; SIM-HARN for the two-host in-process replay. No DEVICE row is available.

**What remains unprovable.** The store is per install; two devices or two installs do not share a replay history. A rooted device can edit stored rows. The invite remains a bearer credential usable by its holder under that holder's own key inside the bucket; durability of the proof id does not change that. Clock manipulation outside the five-minute tolerance, a wiped store and any device-level join observation stay outside this evidence.

**Landed in part (2027-01-12).** `CircleCore.joinProofFailure` reserves the domain-tagged proof digest rather than the carrying event id, so a proof re-signed under a fresh id is refused as `join proof replay`. The reservation shares the bounded set used by `evaluate` and `fresh` and fails closed when that set is full of live entries. A refused proof writes no pin. `ReplayBoundaryTest` records the re-sign case, the captured-proof case and the saturated-set case; the body, signature and bucket rules stay unchanged.

**Still open.** No replay-store port with an atomic `checkAndReserve` exists and no persisted adapter is wired through `ServerCore`. Single-use is still process-local, bounded by `MAX_SEEN`, with the bucket as the stateless backstop. There is no two-host shared-store run and no host reconstructed over a persisted store. No DEVICE row exists.

## Gap 4 — replay state limitation

**Current code path.** `CircleCore.evaluate` at `CircleCore.kt:612-627` and its alias `accept` at `:637-640` reserve ids in the same `seen` map, with FIFO eviction at `:621-624` and `:653-656` once size exceeds `MAX_SEEN = 4096` (`:33`). `fresh` at `:650-658` shares that map. `clear` at `:661` forgets everything. `PanicCore` has the same design at `protocol/src/main/kotlin/app/flit/share/protocol/panic/PanicCore.kt:27` and `:156`. `docs/SECURITY.md:258-268` states that the sets are process memory and that the six-hour window is the backstop.

**Concrete change.** Generalize the port from Gap 3 into a seen-id store used by `evaluate`, `accept` and `fresh`. Keep the in-memory bounded map as the fast path; on a miss consult the durable store, and on `Accept` write both. Prune durable rows older than `REPLAY_WINDOW_MS` (six hours, `CircleCore.kt:27`) and cap row count above `MAX_SEEN` with headroom. Preserve the decision order Invalid → OutsideWindow → Duplicate → Accept and the rule that only Accept records, documented at `CircleCore.kt:597-611`; keep the production order `validShape → verify → evaluate → store` at the callers. An unavailable durable store refuses rather than falling back silently when the durable mode is selected. No wire change.

**Tests to add.** PURE tests in `CircleCoreTest` and `CircleHardeningTest`: accept an id in one instance, evict thousands of other ids or reconstruct the object, then assert the id is Duplicate; assert Invalid and OutsideWindow never reserve; assert the existing overflow-safe window cases at `CircleHardeningTest.kt:221-239` still pass; assert the durable row bound and concurrent reservation. SIM-HARN tests drive two production host instances over one store in-process and assert a duplicate event is refused after reconstruction, with a persisted-file round trip in the harness.

**Evidence label attainable.** PURE for the store-backed reducer and bounds; SIM-HARN for the two-host in-process duplicate. No DEVICE row is available.

**What remains unprovable.** Durability is within one install and one store; a reinstall or a second device has no shared history. Forged timestamps from a compromised peer, store rollback by an attacker with local access, throughput under a flood larger than the harness campaign and any phone lifecycle behavior are not covered. A bounded store proves bounded memory, not absence of replay after its retention window.

**Landed in part (2027-01-12).** `CircleCore.evaluate` reserves with a `reserved-until` deadline and purges only expired entries, so a flood of fresh ids cannot evict the replay record of an event still inside its window. A saturated set returns `Decision.Full` instead of admitting a newcomer. The decision order `validShape → verify → evaluate → store`, the `Invalid → OutsideWindow → Duplicate → Full → Accept` precedence and the rule that only Accept records are unchanged. `ReplayBoundaryTest` records the live-id flood, the retain deadline, the future-skew window and the JOIN cases.

**Still open.** No durable seen-id store, no pruning of persisted rows by `REPLAY_WINDOW_MS`, no app-side adapter and no two-host in-process duplicate case exist. State remains process memory and is lost on restart. No DEVICE row exists.

## Gap 5 — pin cache source

**Current code path.** `TlsIdentity.panicPins` is a single `PinCache(MAX_PINS)` at `TlsIdentity.kt:200`, with `MAX_PINS = 512` at `:188` and the access-ordered `LinkedHashMap` at `:297-324`. `pin` at `:202-207` writes only that map; `pinned` at `:209` reads it; `verifySignature` at `:337-342` fails when a bare fingerprint is absent. `verifyWithCertificate` at `:228-229` deliberately bypasses it. **Concrete change.** Add a durable pin source and make the LRU a cache over it. Extend the persisted rows or add a bounded pin-store file that carries the certificate DER bound to its own digest, written only after verification against an out-of-band fingerprint from QR pairing or an explicit trusted-device action. **Still open.** No durable pin source and no persisted certificate-DER store exist. `PinCache` is not hydrated from a persisted source at startup, so a bare verify after restart or eviction still returns false. No rotation rule driven by an out-of-band fingerprint confirmation is implemented, and no harness case reloads a pin store in-process. No DEVICE row exists.
